A. TARGET ARCHITECTURE
Diagnóstico. El proyecto ya tiene una base valiosa: Dashboard Institucional separado de /operacion, ETL reproducible, datasets curados, integración de infraestructura, canchas, mallas Ponte Pila/PILARES y una UI operativa mobile-first. La debilidad central es que Operación aún es cliente/local: localStorage, usuarios mock, evidencia local, sin DB, sin API, sin auth real, sin auditoría server-side y sin seguridad por ámbito. La deuda metodológica principal es el riesgo de leer mallas como uso, demanda o preferencia. Las mallas son oferta programada; inscritos son participación registrada; asistencia es uso observado; listas de espera/solicitudes son demanda revelada; preferencias requieren encuesta directa; infraestructura no equivale a uso.
Arquitectura objetivo. Mantener Next.js para los frontends: Dashboard Institucional y Operación pueden convivir en la misma app visual, con design system compartido, pero con dominios desacoplados. Operación deja de ser export estático cuando tenga login, escritura, evidencia y offline; requiere runtime Node o backend separado. El Dashboard puede seguir export estático o SSR/ISR leyendo snapshots agregados. Recomendación: backend dedicado para Operación, integrado por API, para no contaminar el Dashboard con lógica transaccional.
Capas. Frontend institucional: solo lectura, mapas, KPIs, metodología, comparativos y marts agregados. Frontend operativo: agenda, clases, alumnos, asistencia, evidencia, incidencias, supervisión y RH. Backend/API: auth, RBAC, scopes, transacciones, auditoría, importaciones, sincronización. DB: PostgreSQL. Storage: evidencia en bucket privado tipo S3/R2/Supabase Storage con URLs firmadas. ETL: conserva fuentes crudas, normaliza catálogos, genera snapshots y marts. Analytics bridge: publica solo agregados curados hacia Dashboard. Observabilidad: logs, métricas, trazas, alertas, errores cliente/API. Backups: DB diarios, storage versionado, pruebas de restore.
cPanel. cPanel puede seguir sirviendo el Dashboard estático y/o actuar como hosting del frontend. Para Operación productiva conviene API externa o subdominio backend con Node compatible. Si cPanel no soporta Node estable, usar backend administrado fuera de cPanel y dejar cPanel como capa web.
Modelo de datos final. Entidades base: users, staff_profiles, role_assignments, territories, venues, disciplines, class_groups, schedule_slots, students, guardians, enrollments, attendance_sessions, attendance_records, evidence_assets, incidents, staff_assignments, substitutions, waiting_lists, demand_requests, surveys, audit_events, analytics_marts. Todas requieren ID estable, fuente, vigencia, fechas de creación/actualización, autor, estado, versión de importación y clasificación de sensibilidad.
Reglas por entidad. users autentica; staff_profiles representa personal; role_assignments une usuario, rol, territorio y vigencia; venues y territories dan ámbito; class_groups agrupa oferta; schedule_slots versiona horarios; students/guardians son datos sensibles; enrollments registra participación inscrita; attendance_sessions/records registran uso observado; evidence_assets guarda prueba documental con retención; incidents gestiona eventos; waiting_lists/demand_requests modelan demanda revelada; surveys modela preferencias declaradas; audit_events es inmutable; analytics_marts contiene solo agregados publicables.
RBAC + ámbito. profesor_promotor: ve y captura solo sus clases, alumnos asignados, asistencia, evidencia e incidencias; no exporta nominal salvo permiso. coordinador: ve sedes/zona, valida pendientes, corrige con auditoría y aprueba cambios menores. subcoordinador: supervisión operativa limitada por zona/sede. lcpo: operación de sede, seguimiento de personal, clases y cumplimiento. rh: ve personal, asignaciones, incidencias administrativas; debe tener mínimo acceso a alumnos. direccion: ve agregados, cumplimiento, mapas y métricas no nominales por defecto. superadmin: administra catálogos, roles, alcances, importaciones, correcciones y auditoría. Toda corrección retroactiva, exportación nominal, reasignación, sustitución, baja y edición de asistencia requiere auditoría; algunas requieren aprobación.
Flujos. Profesor: login, agenda del día, clase, pase de lista, evidencia, incidencia, borrador offline, sincronización. Coordinador/subcoordinador/LCPO: tablero de pendientes, clases no capturadas, sustituciones, evidencias, validación y correcciones. RH: personal, altas/bajas operativas, asignaciones, historial. Dirección: lectura ejecutiva sin nominales, alertas y exportes agregados. Superadmin: catálogos, usuarios, permisos, importaciones, auditoría. Alumno/tutor, si aplica: inscripción, consentimiento, estado de participación, avisos y baja, con acceso separado y mínimo.
Mobile/offline. La experiencia debe abrir en agenda del día, navegación inferior, acciones rápidas, buscador de clase/alumno, captura de foto comprimida, borradores locales cifrados, cola de sincronización, estados “pendiente/sincronizado/error”, resolución de conflicto por timestamp de servidor y aprobación cuando afecte historial. Diseño limpio tipo Apple/Linear/Notion/Stripe: poco texto, jerarquía clara, controles grandes, accesibilidad, contraste, uso con una mano.
Privacidad y seguridad. Minimización estricta; datos personales clasificados por sensibilidad; Dashboard sin nominales; seudonimización en marts; cifrado en tránsito y reposo; URLs firmadas para evidencia; logs inmutables; retención definida para fotos, incidencias y asistencia; MFA futuro para roles altos; política de correcciones; consentimiento fotográfico y tratamiento de menores deben validarse con jurídico/protección de datos. No fijar criterios legales sin revisión institucional.
Analytics bridge. Operación alimenta Dashboard solo por agregados diarios/semanales/mensuales: clases programadas, impartidas, tasa de impartición, listas capturadas, asistencia media, ocupación, altas/bajas, demanda no atendida, cobertura por sede/alcaldía, horas impartidas, cancelaciones, incidencias, evidencia y continuidad. MVP: clases programadas, listas capturadas, impartición, evidencia, pendientes. Requiere madurez: retención, ocupación real, demanda no atendida, impacto, preferencias y comparativos finos. Quality gates: completitud, duplicados, rangos válidos, coherencia horario-sede-profesor, anonimización y aprobación de publicación.
